<objective>
Turn `/api/upload` from a completely open endpoint into a gated one. Today anyone on the internet can
POST a file of any size and any type into a personal S3 bucket — this is the single highest-risk surface
in the codebase and the reason this phase exists.

Five gates land here, ordered cheapest-first and ALL before the S3 put: session (401) → size (413) →
magic bytes (415) → quota (413) → rate limit (429) → S3 put → `Upload.create`.

Purpose: nothing reaches S3 without a valid session, an allowlisted image type verified by its bytes, a
size under the cap, and quota remaining.
Output: a rewritten `app/api/upload/route.js`.
</objective>

  <action>
Rewrite the handler with the first three gates. Keep the existing structure recognisable — this is a
guarded version of the same flow, not a new architecture.

Order and behaviour:

1. **No-file** — replace the implicit-200 branch at lines 32-34 with `Response.json({ error: 'No file
   provided' }, { status: 400 })`. The current implicit 200 is the same class of bug as SEC-08.

2. **Session (SEC-01, D-09)** — call `requireSession()` FIRST, before `req.formData()`. Returning early
   avoids parsing a multipart body for a request that has no business here. On `null` return
   `Response.json({ error: 'Authentication required' }, { status: 401 })`.

3. **Size (SEC-02, D-10)** — a `MAX_UPLOAD_BYTES` constant of `4 * 1024 * 1024`. Check `file.size` from
   the FormData entry, which is available BEFORE the stream is read — do not buffer 4 MB in order to
   reject it. Over the cap: `Response.json({ error: 'File too large — maximum 4 MB' }, { status: 413 })`.
   Add a comment recording that 4 MB sits deliberately under Vercel's 4.5 MB platform limit so our
   readable 413 fires instead of the platform's opaque one.

4. **Buffer, then magic bytes (SEC-03, D-13, D-14)** — keep the existing `for await (const chunk of
   file.stream())` loop and `Buffer.concat(chunks)`, then call `detectImageType(buffer)`. On `null`:
   `Response.json({ error: 'Only JPEG, PNG and WEBP images are allowed' }, { status: 415 })`.

5. **The detected type becomes authoritative** — this resolves RESEARCH.md Planner Decision Point 5 in
   favour of yes. Both of the following change:
   - The object key's extension comes from `detected.ext`, NOT from `file.name.split('.').pop()` at
     line 16. Keep `uuidv4()` as the key stem.
   - `ContentType` on the `PutObjectCommand` is `detected.mime`, NOT `file.type` at line 28.
   Without both, a caller can send PNG-magic bytes with `Content-Type: image/svg+xml` and S3 will store
   and serve it as SVG — which is exactly the stored-XSS vector D-13/D-15 exist to close, since D-15
   keeps objects `public-read`. Never read `file.type` or `file.name` for any decision; the only
   remaining legitimate use of `file` is `file.size` and `file.stream()`.

6. `ACL: 'public-read'` stays (D-15) — presigned URLs would have to be regenerated per render on the
   public page and would break caching and `next/image`.

Import `s3Client` and `BUCKET_NAME` from `@/lib/s3` (plan 01-01 already did this extraction; do not
reintroduce an inline client).

Add the last two gates and the record write, continuing after Task 1's magic-byte check.

4. **Quota (SEC-04, D-11, D-16)** — a `QUOTA_BYTES` constant of `25 * 1024 * 1024`. `await
   connectToDatabase()`, then sum the owner's existing bytes with
   `Upload.aggregate([{ $match: { owner: session.user.email } }, { $group: { _id: null, total: { $sum:
   '$size' } } }])`, treating an empty result as 0. If `total + file.size > QUOTA_BYTES`, return
   `Response.json({ error: 'Upload limit reached (25 MB) — replace an existing image' }, { status: 413 })`
   using D-16's exact wording. Deleting to free quota is Phase 1.5; do not build it here.

5. **Rate limit (SEC-05, D-19, D-20)** — `const key = rateLimitKey('upload', session, req)` then
   `const { allowed, retryAfter } = await checkRateLimit('upload', key)`. When not allowed, return
   `Response.json({ error: 'Too many uploads — please wait' }, { status: 429, headers: { 'Retry-After':
   String(retryAfter) } })`. The header is required by D-20 and asserted by `--sec05`.

6. **S3 put, THEN the record** — after a successful `PutObjectCommand`, `await Upload.create({ owner:
   session.user.email, key: newFileName, size: file.size, url: link })`. Order is load-bearing: creating
   the record before the put means a failed put permanently burns quota that no object occupies. Wrap the
   put so a thrown S3 error returns `Response.json({ error: 'Upload failed' }, { status: 502 })` and no
   record is written.

Add a `ponytail:` comment on the quota check naming the race: two concurrent uploads can both pass the
check and jointly exceed the cap. Blast radius is one extra file, bounded at 4 MB. Atlas free tier is a
replica set so a transaction is available, but it is not worth it for a 4 MB overshoot — the upgrade path
is a transaction or a conditional update if quota ever becomes billable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → `POST /api/upload` | today entirely unauthenticated; the file bytes, declared type, filename and size are all attacker-controlled |
| upload handler → S3 bucket (`public-read`) | anything stored here is served to the public internet under the app's domain reputation |
| upload handler → the S3 bill | every stored byte is a cost the owner pays |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Spoofing | anonymous POST to `/api/upload` | mitigate | `requireSession()` before `req.formData()`; 401 with nothing read |
| T-04-02 | Tampering | `ContentType` taken from client `file.type` (line 28) | mitigate | `ContentType` and the key extension both come from `detectImageType`; `file.type` and `file.name` are never read |
| T-04-03 | Tampering | stored SVG served `public-read` as executable script | mitigate | Magic-byte allowlist of jpeg/png/webp only (D-13); SVG has no accepted signature |
| T-04-04 | Denial of Service | unbounded file size filling the bucket | mitigate | 4 MB `file.size` gate before buffering, plus Vercel's 4.5 MB platform ceiling above it |
| T-04-05 | Denial of Service | unbounded object count per account | mitigate | 25 MB byte quota via `Upload.aggregate` before the put |
| T-04-06 | Denial of Service | rapid repeat uploads inside quota | mitigate | `checkRateLimit('upload', ...)` at 10/min → 429 + `Retry-After` |
| T-04-07 | Elevation of Privilege | quota race between concurrent invocations | accept | Bounded at one extra ≤4 MB file; documented `ponytail:` with a transaction as the upgrade path |
| T-04-08 | Information Disclosure | S3 error text leaking bucket or credential detail to the client | mitigate | The S3 catch returns a generic `Upload failed` 502; detail goes to the server log only |
| T-04-SC | Tampering | npm installs | mitigate | Zero new dependencies — `detectImageType` is hand-written per D-14 rather than adding `file-type` |
</threat_model>
