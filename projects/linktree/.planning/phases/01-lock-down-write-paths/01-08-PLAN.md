<objective>
Throttle the three page-save actions and make every refusal in this phase visible to the user. A silent
failure is worse than a loud one: D-20 exists because a legitimate user must not believe a save succeeded
when it did not.

Two refusal shapes are required, and the asymmetry is the whole reason D-30 rejected middleware. Route
handlers can set headers, so `/api/upload` refuses with a status plus `Retry-After`. Server actions return
values, not responses, so the three `PageAction.js` exports must return a refusal object and the calling
component raises the toast. Those three exports currently return bare booleans, so their contract changes
and all three callers need updating.

Purpose: rapid repeat writes are throttled, and every gate built in this phase produces a message a human
can act on.
Output: gated `action/PageAction.js`, three updated form components, and a `lib/upload.js` that pre-checks
size and maps every status to a toast.
</objective>

Add a module-local `async function checkSaveGate()` in `action/PageAction.js` (not exported, so it does not
become a fourth server action). It:
1. Calls `requireSession()`. On `null` returns `{ allowed: false, result: { success: false, error:
   'Authentication required' } }`.
2. Calls `rateLimitKey('pageSave', session)` — no `req` exists in a server action, so the key is the
   session email. All three actions pass the SAME action name `'pageSave'`, so they deliberately share one
   30/min bucket: D-19's limit is per user for saving a page, not per form.
3. Calls `checkRateLimit('pageSave', key)`. When not allowed returns `{ allowed: false, result: { success:
   false, error: 'Too many saves — please wait a moment', retryAfter } }`.
4. Otherwise returns `{ allowed: true, session }`.

Call `checkSaveGate()` as the FIRST statement in each of `SavePageSetting`, `SavePageButton` and
`SavePageLinks`, returning `gate.result` immediately when `gate.allowed` is false. Then use `gate.session`
in place of each function's own `getServerSession` call, so the session is read once per invocation.

**Return contract change.** Every path in all three exports must now return
`{ success: boolean, error?: string, retryAfter?: number }` instead of a bare boolean. Convert every
existing `return true` to `{ success: true }` and every existing `return false` to `{ success: false,
error: '<the reason that branch represents>' }` — read each branch and give it an accurate message rather
than one generic string. A server action cannot set a `Retry-After` header, which is why `retryAfter` rides
on the object; Task 2's callers turn it into a toast.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client component → server action | the action is a public POST endpoint under the hood; a caller can invoke it directly without the form |
| server action → the `pages` collection | authenticated but previously unthrottled writes |
| server error text → the browser toast | server-supplied strings are rendered to the user |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01 | Denial of Service | unthrottled repeat page saves | mitigate | One shared `checkSaveGate` applying `checkRateLimit('pageSave', ...)` at 30/min to all three exports |
| T-08-02 | Spoofing | a save action invoked without a session, bypassing the form | mitigate | `requireSession()` inside the shared gate runs before any write, in every export |
| T-08-03 | Repudiation | a throttled save appearing to succeed | mitigate | Every action returns `{ success: false, error }` and all three callers now toast it; `PageButtonForm` and `PageLinkForm` stop discarding the result |
| T-08-04 | Tampering | the client size pre-check being bypassed | accept | Deliberate — the pre-check is UX only, and plan 01-04's server gate is the real enforcement. Both use the identical 4 MB constant so they cannot drift |
| T-08-05 | Information Disclosure | server error strings rendered into a toast | mitigate | Only the curated messages from plans 01-04 and 01-06 are surfaced; the S3 failure path returns a generic `Upload failed` with detail kept server-side |
| T-08-06 | Elevation of Privilege | `RATE_LIMIT_*` overrides left set after testing | mitigate | Plan 01-03 honours them only when `NODE_ENV !== 'production'`, and the checkpoint requires removing them |
| T-08-07 | Tampering | a client-supplied `x-amz-acl` header implying client control of object visibility | mitigate | The header is removed; the ACL is set server-side on the `PutObjectCommand` per D-15 |
| T-08-SC | Tampering | npm installs | mitigate | Zero new dependencies — `react-toastify` is already installed and already wired into `lib/upload.js` |
</threat_model>
