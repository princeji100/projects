## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Trusting a handoff's "no live DB needed" claim | The 2026-08-10 handoff called plan 01-03 "pure logic and schema definitions — no live DB or S3 access". True of its Task 1 (models), wrong about Task 2: the limiter self-check calls `checkRateLimit` → `lib/connectToDB.js` → `process.env.MONGODB_URI`. Caught before dispatch, not after. | advisory | Before dispatching any plan, read its `<verify>` blocks — not just its objective. A plan that writes pure logic can still *verify* against live infrastructure. |
| Pre-empting a deferred destructive plan | 01-02 Task 3 imports `../lib/s3.js`, which plan 01-01 creates. 01-01 is the wipe plan. Creating `lib/s3.js` "to unblock Task 3" would put a file the wipe plan owns into the tree ahead of it. | advisory | Import it lazily via dynamic `await import()` wrapped to print SKIP on failure. Never create a deferred plan's artifacts early — especially not a destructive plan's. |
| Self-defeating grep assertion | Task 1's acceptance criteria demand `grep -c "file-type" lib/magicBytes.js` return 0. The comment explaining *why no dependency was added* contained that literal string and failed the check that proves it. | advisory | When a criterion greps for an absent string, check comments and docstrings too — not just code. |
