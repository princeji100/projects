<objective>
Wipe all pre-existing application data — the `pages`, `users`, `events`, `accounts` and `sessions`
collections plus every object in the S3 bucket — before any gate is built. This is SEC-12 and it runs
FIRST and ALONE, because every other plan in this phase is easier on an empty database: no upload
backfill (D-08), no username migration (D-25), and no stale sessions surviving the new allowlist.

Purpose: start from a known-empty state so quota accounting, the allowlist, and the username rules
never have to tolerate legacy data.
Output: `lib/s3.js` (shared client, also needed by Phase 1.5's delete UI) and `scripts/wipe.js`.
</objective>

  <action>
Resolves RESEARCH.md Planner Decision Point 4 in favour of a required confirmation flag (D-07:
irreversible, must be explicit and reviewable).

Create `scripts/wipe.js`, a plain node script run as `node scripts/wipe.js --yes-destroy-everything`.
It must NOT be wired into `package.json` scripts — an npm alias makes accidental invocation easier.

Behaviour:
1. If `process.argv` does not contain the exact string `--yes-destroy-everything`, print a refusal
   naming the flag and `process.exit(1)` without touching anything.
2. Mongo phase: connect once via `mongoose.connect(process.env.MONGODB_URI)` (this is a standalone
   node script outside Next, so it does not use `lib/connectToDB.js`; that helper is for request
   paths). Then drop the collections `pages`, `users`, `events`, `accounts`, `sessions` by name via
   `mongoose.connection.db.collection(name).drop()`. Wrap each drop individually and treat
   `NamespaceNotFound` (error code 26 / message containing `ns not found`) as SUCCESS, printing
   `already absent`. Per RESEARCH.md § Unresolved, mongoose's `User` model and the NextAuth adapter
   very likely share the single `users` collection — dropping by name once handles both, and a
   missing collection must not fail the run.
3. S3 phase: import `s3Client` and `BUCKET_NAME` from `../lib/s3.js`. Loop
   `ListObjectsV2Command({ Bucket: BUCKET_NAME, ContinuationToken })`; for each page, if
   `Contents?.length`, send `DeleteObjectsCommand({ Bucket, Delete: { Objects: Contents.map(o => ({ Key: o.Key })) } })`.
   Continue while `IsTruncated`, passing `NextContinuationToken`. Batch size is naturally ≤1000
   because a list page is ≤1000.
4. Print a final summary line per collection and the total object count deleted, then
   `await mongoose.disconnect()` and exit 0.
5. Catch `AccessDenied` / `403` from either S3 command specifically and print a remediation message
   naming the two IAM actions required: `s3:ListBucket` on the bucket ARN and `s3:DeleteObject` on
   `arn:aws:s3:::<bucket>/*`. Per RESEARCH.md § Unresolved this is an EXPECTED first-run outcome (the
   key has only ever done `PutObject`), not a code bug — exit non-zero so it is visible, but do not
   treat it as a defect in this script.

Add a `ponytail:` comment noting the script is single-run Phase 1 scaffolding and that Phase 1.5's
delete UI will reuse `lib/s3.js` rather than this script.
  </action>
