<objective>
Make signup invite-only. Everything in this project runs on free tiers, so an unbounded user count is the
real bill risk — per-user quotas bound the cost of each account but not how many accounts exist. A
`signIn` callback checks the `AllowedUser` collection and refuses anything not on it, and the refusal
shows a human message on the existing login page rather than NextAuth's default error screen: a recruiter
opening the live link must see a working app.

This reverses the locked PROJECT.md decision "signup stays open to anyone with a Google account" (D-02).
The multi-tenant architecture is untouched — only the door is gated, and public pages stay public.

Purpose: bound `N`, the one cost variable quotas cannot bound.
Output: the allowlist callback, the login-page message, a seed script, and the PROJECT.md correction.
</objective>

<interfaces>
NextAuth v4 (`next-auth` ^4.24.7 — v4 semantics, NOT v5/Auth.js).

`signIn` callback return values, per https://next-auth.js.org/configuration/callbacks:
  `true`  → sign-in proceeds
  `false` → blocks sign-in and shows the default error message
  a string URL → redirect, cancelling the auth flow
Returning `false` produces the `AccessDenied` error code — one of exactly four error-page codes, which
the pages docs describe as "usually occurs when you restricted access through the signIn callback".
This is the mechanism D-03 relies on. Do NOT spec a throw-based design: RESEARCH.md § Unresolved records
that v4's throw behaviour is undocumented and unverified.

`AccessDenied` lands on the ERROR page, not the sign-in page — sign-in-page errors are a separate list.
So `authOptions.pages` must point BOTH at `/login`:
  `pages: { signIn: '/login', error: '/login' }`
The docs require the listed routes to really exist; `/login` does, at `app/(default)/login/page.js`
(the `(default)` route group does not appear in the URL).

The existing callback at lines 28-33 is a no-op returning `true` whenever `user.email` is truthy — the
change replaces its body, it does not add a callback.

`adapter: MongoDBAdapter(clientPromise)` at line 8 means DATABASE sessions, not JWT. Sessions are rows in
the adapter's `sessions` collection. This is why plan 01-01's wipe invalidates live logins.

`app/(default)/login/page.js` is already `'use client'` (line 1) and already calls `useSession()` (line 7)
and `redirect('/')` (line 10). `useSearchParams()` in App Router requires a `<Suspense>` boundary or
`npm run build` fails during static generation — a build-breaking trap, not an ignorable warning.
</interfaces>

New behaviour:
1. If `!user?.email`, return `false` (keep the existing presence check).

`clientPromise`: it keeps the read consistent with D-30's `lib/` helpers and the `models?.X || model(...)`
idiom, and `lib/connectToDB.js` is idempotent so the auth handshake does not open a second connection.
`signIn` runs on the Node runtime, so mongoose is available.

Also add to `authOptions`, as a sibling of `callbacks`:
  `pages: { signIn: '/login', error: '/login' }`
Without the `error` entry the refusal lands on NextAuth's default error page, which D-03 rejects.

Add a `ponytail:` comment recording the real ceiling: `signIn` fires at login, not per request, so
removing an email from the allowlist does not evict a live session. Out of scope for Phase 1 (D-05 makes
the allowlist insert-only) but it interacts with Phase 1.5's remove-email UI, which will need to delete
that user's `sessions` rows to take effect.

Do NOT add an `isAdmin` field, a role table, or any admin check in this file. D-04 makes admin identity a
single `ADMIN_EMAIL` env var compared against the session email, and its only consumer is Phase 1.5's
admin page. One admin does not need a role system.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Google OAuth identity → the app's user table | any Google account holder can initiate the flow; the app decides who becomes a user |
| `?error=` query string → rendered login page | the value is attacker-controlled and reaches the DOM |
| local shell → `allowedusers` | the seed script grants app access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | anyone with a Google account becoming a user | mitigate | `signIn` returns `false` unless `AllowedUser.findOne` matches the lowercased email |
| T-05-02 | Spoofing | email case variance bypassing the allowlist | mitigate | `lowercase: true` on the model plus `toLowerCase()` on the lookup and in the seed script |
| T-05-03 | Denial of Service | allowlist DB error admitting a stranger | mitigate | The callback fails CLOSED — a lookup error returns `false`, deliberately opposite to the limiter's fail-open |
| T-05-04 | Tampering | reflected XSS via the `?error=` value | mitigate | The value is compared against the literal `'AccessDenied'`; it is never interpolated into the DOM. All other values render fixed copy |
| T-05-05 | Information Disclosure | the refusal message revealing whether an email is on the list | accept | The copy is identical for every refused email — it states the app is invite-only, not whether that address exists |
| T-05-06 | Elevation of Privilege | a removed allowlist entry not evicting a live database session | accept | Documented `ponytail:` ceiling; the allowlist is insert-only in Phase 1 per D-05, and Phase 1.5's remove UI must delete `sessions` rows |
| T-05-SC | Tampering | npm installs | mitigate | Zero new dependencies — `useSearchParams` and `Suspense` ship with Next, and the allowlist read uses the installed mongoose |
</threat_model>
