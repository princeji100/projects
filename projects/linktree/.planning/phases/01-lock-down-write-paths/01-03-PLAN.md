<objective>
Create the three new collections and the two shared gate helpers every later plan in this phase calls.
This is the foundation layer: nothing here modifies a write path, so it runs in parallel with plan 01-02
and unblocks plans 01-04 through 01-08.

The load-bearing work is the rate limiter. MongoDB's TTL monitor sweeps only about every 60 seconds, so
an expired document stays readable — a naive "upsert then read count" limiter is silently wrong for up
to a full window. The limiter must filter on `expiresAt` in its own query.

Purpose: one correct limiter and one correct session read, called from five write surfaces.
Output: `models/Upload.js`, `models/RateLimit.js`, `models/AllowedUser.js`, `lib/requireSession.js`,
`lib/rateLimit.js`.
</objective>

**`lib/requireSession.js`** (D-30) — export `async function requireSession()` returning the session
object or `null`. It calls `getServerSession(authOptions)` exactly as `action/PageAction.js:11` does and
returns `null` when `session?.user?.email` is falsy. It does NOT throw and does NOT construct a
`Response` — the two write surfaces need different refusal shapes (a 401 Response from route handlers,
a returned object from server actions), so the helper stays shape-agnostic and each caller builds its
own refusal.

**`lib/rateLimit.js`** (D-17, D-18, D-19) — three exports.

`LIMITS` — a frozen object of `{ windowMs, max }` per action, from D-19:
  `upload: { windowMs: 60_000, max: 10 }`
  `pageSave: { windowMs: 60_000, max: 30 }`
  `claim: { windowMs: 3_600_000, max: 5 }`
  `click: { windowMs: 60_000, max: 60 }`
Both values must be overridable from the environment so VALIDATION.md's Wave 0 requirement holds — the
5/hour claim limit has to be exercisable in seconds, not an hour. Read `RATE_LIMIT_WINDOW_MS` and
`RATE_LIMIT_MAX_OVERRIDE`; when either is set and parses as a positive integer, it replaces that field
for EVERY action. Guard the override so it cannot apply in production: only honour it when
`process.env.NODE_ENV !== 'production'`. Log once at module load when an override is active.

`rateLimitKey(action, session, req)` (D-18) — returns `` `${action}:${identifier}` ``. The identifier is
`session.user.email` when present, otherwise the client IP. Namespacing by action is required or a user
shares one bucket across upload and page save. Derive the IP from the `x-forwarded-for` header, taking
the FIRST comma-separated entry and trimming it — on Vercel this header is a proxy chain, and using the
whole string would key on a value an attacker can extend. Fall back to the literal string `'unknown'`
when the header is absent, so an unheadered request is still limited rather than unlimited. Server
actions have no `req`; when `req` is undefined the session email is the only source and an
unauthenticated action call must key on `'unknown'`.

`checkRateLimit(action, key)` — returns `{ allowed: boolean, retryAfter: number }` where `retryAfter` is
whole seconds until the window ends. Implementation, per RESEARCH.md's trap:

1. `await connectToDatabase()` from `lib/connectToDB.js`.
2. `const now = new Date()`; look up `{ windowMs, max }` from `LIMITS[action]`.
3. One atomic `RateLimit.findOneAndUpdate` with
   filter `{ key, expiresAt: { $gt: now } }`,
   update `{ $inc: { count: 1 }, $setOnInsert: { key, expiresAt: new Date(now.getTime() + windowMs) } }`,
   options `{ upsert: true, new: true, setDefaultsOnInsert: true }`.
   The `expiresAt: { $gt: now }` in the FILTER is the whole point: a stale document fails the filter,
   so the upsert path fires and a fresh window starts at `count: 1`. TTL deletion becomes pure garbage
   collection and is never correctness-bearing. Do NOT filter on `{ key }` alone and then compare
   `expiresAt` on the returned document — that increments a stale count before you can see it.
4. Catch a duplicate-key error (`err.code === 11000`) and retry the same operation exactly ONCE. The
   race is two lambdas both missing the filter and both attempting the insert; the loser's retry finds
   the winner's document and increments it. Do not loop more than once — a second E11000 is a real
   fault, so rethrow.
5. `allowed` is `doc.count <= max`. `retryAfter` is
   `Math.max(1, Math.ceil((doc.expiresAt - now) / 1000))` — never 0, because a `Retry-After: 0` tells a
   client to retry immediately.
6. Wrap the whole body so a database failure does NOT block writes: on an unexpected error, log it and
   return `{ allowed: true, retryAfter: 0 }`. Fail-open is the right call for a limiter on a personal
   project — a Mongo blip must not make the app unusable. Add a `ponytail:` comment naming this choice
   and noting that a security-critical deployment would fail closed instead.

Add a `ponytail:` comment naming the fixed-window ceiling (2x burst at a boundary) and pointing at a
sliding window as the upgrade path if D-19's headroom ever stops being enough.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client `x-forwarded-for` → limiter key | header is client-supplied on any non-proxied path and a proxy chain on Vercel |
| concurrent serverless invocations → single RateLimit document | two lambdas race on the same key with no shared memory |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Spoofing | `rateLimitKey` IP derivation | mitigate | Take only the FIRST `x-forwarded-for` entry (Vercel's own appended client IP); an attacker-prepended chain cannot shift the key. Absent header keys to `'unknown'` so the request is still limited |
| T-03-02 | Tampering | concurrent upsert on the same key | mitigate | `{ key: 1 }` unique index plus a single E11000 retry — without the index the limit silently doubles |
| T-03-03 | Elevation of Privilege | reading a TTL-expired document as an active window | mitigate | Filter includes `expiresAt: { $gt: now }`; TTL deletion is garbage collection only |
| T-03-04 | Elevation of Privilege | `RATE_LIMIT_MAX_OVERRIDE` set in production to disable limits | mitigate | Override honoured only when `NODE_ENV !== 'production'`, and logged at module load |
| T-03-05 | Denial of Service | limiter DB failure blocking all writes | accept | Fail-open with a logged error; documented `ponytail:` ceiling — a fail-closed posture is the upgrade path for a higher-stakes deployment |
| T-03-06 | Denial of Service | boundary burst reaching 2x the limit | accept | Fixed window, documented `ponytail:`; D-19's limits have enough headroom that 2x is still far below abuse |
| T-03-SC | Tampering | npm installs | mitigate | Zero new dependencies (D-17 forbids Redis; the limiter uses the installed mongoose). `package.json` must be unchanged |
</threat_model>
