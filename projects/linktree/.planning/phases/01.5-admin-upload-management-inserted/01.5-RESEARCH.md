## User Constraints
- **D-02:** The `AppSidebar` renders an "Admin" link/tab *only* when the authenticated user's email matches `process.env.ADMIN_EMAIL`.
- **D-03:** Hiding UI elements is not security — authorization must be strictly enforced server-side on the page component and in every admin server action/API route.
- **D-07:** When an admin removes an email from the allowlist, the `AllowedUser` document is deleted and all active database sessions for that user (in NextAuth's `sessions` collection) are immediately deleted/revoked.
- **D-08:** Existing user data (`Page`, `Upload` records, and S3 objects) is **preserved** upon allowlist removal.
- **D-15:** Before deleting an upload, the server and client inspect the user's `User` (avatar) and `Page` (`bgImage`, `links[].icon`) records to detect active references.
- **D-17:** On confirmed deletion: 1. Verify ownership. 2. Delete S3 object via `DeleteObjectCommand`. 3. Delete `Upload` document. 4. Clear references in `User` and `Page`.

## Summary
This phase introduces the Admin and Upload management screens. No new external packages or services are introduced. The core technical requirements are implementing Next.js Server Actions for secure database mutations (Mongoose) and S3 object deletions (`@aws-sdk/client-s3`), while enforcing strict authorization via the existing `requireSession` helper and environment variables (`ADMIN_EMAIL`).

**Primary recommendation:** Use Next.js Server Actions exclusively for these mutations. Use `DeleteObjectCommand` from `@aws-sdk/client-s3` for file deletion, and Mongoose for coordinated cleanup of references.

## Architecture Patterns

### Pattern 1: Server Actions for Mutations
**What:** Use Next.js server actions (e.g., `removeAllowedUser`, `deleteUpload`) for handling form submissions and deletions.
**When to use:** For all admin and upload management state changes.
**Example:**
```javascript
'use server'
import { requireSession } from '@/lib/requireSession'
import { AllowedUser } from '@/models/AllowedUser'

export async function addAllowedUser(email) {
  const session = await requireSession();
  if (session.user.email !== process.env.ADMIN_EMAIL) throw new Error("Forbidden");
  // ... mutation logic
}
```

### Pattern 2: Reference Cleanup on Deletion
**What:** When deleting an upload, find and unset any references to its URL in the `Page` and `User` models.
**When to use:** During the `deleteUpload` server action.
**Example:**
```javascript
await Page.updateMany(
  { owner: session.user.email, bgImage: upload.url },
  { $unset: { bgImage: "" } }
);
```

## Common Pitfalls

### Pitfall 1: Dangling References
**What goes wrong:** Image is deleted from S3 and the `Upload` collection, but the `Page` model still points to the URL, resulting in broken images on the public profile.
**Why it happens:** Failing to coordinate deletion across all referencing documents.
**How to avoid:** Explicitly `updateMany` or `updateOne` on `Page` and `User` collections to nullify references to the deleted URL before returning success.

### Pitfall 2: Partial Deletion
**What goes wrong:** S3 object is deleted but the database record remains (or vice versa), leading to quota calculation errors.
**Why it happens:** Unhandled promise rejections in the middle of the deletion sequence.
**How to avoid:** Sequence operations carefully. Validate references -> Delete from S3 -> Delete from DB -> Return success.
