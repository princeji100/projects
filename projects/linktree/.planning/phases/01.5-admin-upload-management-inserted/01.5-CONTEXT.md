## Phase Boundary

Phase 1.5 delivers the management UI for the security and storage infrastructure built in Phase 1:
1. **Admin Allowlist UI** (`ADMIN-01`, `ADMIN-02`): An admin-only interface to manage invite-only access.
2. **User Uploads Manager** (`UPLOAD-01`, `UPLOAD-02`): A media storage dashboard to view, track quota, and safely delete uploaded images.

**In scope:**
- Admin page at `/account/admin` to list, add, and remove allowlisted emails, with instant session revocation upon removal.
- Admin navigation tab in `AppSidebar` visible only when authenticated email matches `ADMIN_EMAIL`.
- Strict server-side authorization and fail-closed handling for admin operations (403 for unauthorized API / redirect for unauthorized UI).
- Uploads management page at `/account/uploads` with a 25 MB quota progress bar and responsive thumbnail grid.
- In-use image deletion safety: modal warning displaying all active references (avatar, background, link icons) and automatic reference cleanup on confirmed delete.
- Server-side ownership, MIME/type, and file size enforcement.

**Out of scope:**
- Profile page rendering fixes (Phase 2 FIX-03, FIX-04, FIX-05).
- Form success reporting bug fixes (Phase 2 FIX-01, FIX-02).
- Themes, QR codes, link lifecycle scheduling, or analytics enhancements (Phases 3, 4, 5).

<decisions>
## Implementation Decisions

### Admin Page & Authorization (ADMIN-01, ADMIN-02)
- **D-01:** The Admin Allowlist UI lives at `/account/admin` within the standard authenticated account layout.
- **D-02:** The `AppSidebar` renders an "Admin" link/tab *only* when the authenticated user's email matches `process.env.ADMIN_EMAIL`.
- **D-03:** Hiding UI elements is not security — authorization must be strictly enforced server-side on the page component and in every admin server action/API route.
- **D-04:** If `ADMIN_EMAIL` is unset or invalid in the environment, admin authorization fails closed (no user receives admin access).
- **D-05:** A non-admin who directly navigates to `/account/admin` receives no admin data and is immediately redirected to `/account` with an unauthorized error toast. Unauthorized API calls return `HTTP 403 Forbidden`.
- **D-06:** The admin interface provides:
  - An input to add an email (lowercased, trimmed, validated format, idempotent upsert into `AllowedUser`).
  - A clean table/list of currently allowlisted emails with search/filter and removal action.

### Allowlist Removal & Session Revocation (ADMIN-01, T-05-06)
- **D-07:** When an admin removes an email from the allowlist:
  - The `AllowedUser` document is deleted.
  - All active database sessions for that user (in NextAuth's `sessions` collection) are immediately deleted/revoked.
  - The user is logged out upon their next request or page refresh and cannot re-authenticate.
- **D-08:** Existing user data (`Page`, `Upload` records, and S3 objects) is **preserved** upon allowlist removal. Allowlist removal represents access revocation, not destructive data deletion. If the user is re-invited later, their page and uploads remain intact.
- **D-09:** Protected write routes and pages re-verify allowlist status server-side so an existing token cannot perform actions if the email has been de-listed.

### Uploads Management & Quota Presentation (UPLOAD-01)
- **D-10:** Uploads manager lives at `/account/uploads` and is exposed via an "Uploads" tab in `AppSidebar`.
- **D-11:** The top of `/account/uploads` features a storage quota meter showing:
  - Total bytes used out of the 25 MB quota (`X.X MB / 25.0 MB`).
  - Remaining capacity and visual progress bar (color-coded green -> yellow -> red when near capacity).
- **D-12:** Uploads are presented in a responsive thumbnail grid displaying:
  - Image preview thumbnail.
  - Filename / image type.
  - Formatted file size (KB / MB).
  - Upload date.
  - In-use indicator badge and delete action button.
- **D-13:** Strict server-side ownership: users can query, view, and delete only records where `owner === session.user.email`.
- **D-14:** UI provides dedicated, polished empty states ("No uploads yet"), loading skeletons, error alerts, and quota-exceeded warnings.

### In-Use Image Deletion Safety & Cleanup (UPLOAD-02)
- **D-15:** Before deleting an upload, the server and client inspect the user's `User` (avatar) and `Page` (`bgImage`, `links[].icon`) records to detect active references.
- **D-16:** If the image is currently in use, the confirmation modal lists every active location (e.g., "Used as: Profile Avatar, 2 Link Icons") and requires explicit confirmation.
- **D-17:** On confirmed deletion:
  1. Server verifies ownership and authorization.
  2. The S3 object is deleted via `DeleteObjectCommand`.
  3. The `Upload` document is deleted from MongoDB.
  4. Active references in `User` (avatar) and `Page` (`bgImage`, `links[].icon`) are automatically cleared/reset to null/empty so no broken or stale URLs remain.
- **D-18:** Coordinated error handling: if any deletion step fails, a clear error is returned without reporting partial success.
- **D-19:** After deletion, the storage quota meter and thumbnail grid update immediately without requiring a full page refresh.

### the agent's Discretion
- Modal styling, animation details, and skeleton loaders following established Tailwind CSS patterns.
- Specific icon choices from `@fortawesome/free-solid-svg-icons` (e.g. `faUserShield` for Admin, `faImages` / `faCloud` for Uploads).

</decisions>

## Specific Ideas
- Admin allowlist table should allow quick email lookup and one-click removal with confirmation.
- Uploads gallery cards should show an "In Use" tag/badge if the image URL matches current avatar, background, or link icons.
- Deleting an image in use gracefully clears the field in `Page`/`User` to prevent dead links.
